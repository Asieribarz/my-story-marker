# CLAUDE.md

Specifications for an adventure-story generator: an orchestrator delegates to five declared agents, one page call per page, all durable state lives in files. **The orchestrator is not built yet.** This repository holds the specifications, the configuration, the five agent definitions, and the artefacts of runs that were orchestrated by hand.

Documents are written in English. Conversation may be in Spanish; the files are not.

---

## Where authority lives

Read in this order. When two disagree, the earlier one wins.

1. **`config.json`** — every control and organization value. The only place a number lives.
2. **`specs/functional_specification_story_agent.md`** — what the system does. FR-01 to FR-41.
3. **`specs/technical_specification_story_agent.md`** — how. TR-xx, invariants I-1 to I-9, build inventory (§12).
4. **`specs/self_improvement_specification_story_agent.md`** — the calibration loop that runs *between* runs. It touches one thing inside a run: rule 2 of `page-writer.md`, between its delimiters. Everything else it does happens after a run has closed.
5. **`.claude/agents/*.md`** — what each of the six call types judges and refuses. **The agent file is where that behaviour is defined**; the specs hold the wiring (technical §5) and the inventory (§12.2) and restate none of it. To change how a call behaves, change the agent file. To change what it is handed or what it returns, change both.
6. **`stories/the-cold-lamp/report.md`** — evidence from the run of 2026-09-15. **Never edit it.** It records what happened under specs v2.1, and rewriting it destroys the only measurement the project has.

Run artefacts — `bible/`, `pages/`, `state/`, `story.md` — were produced under config v2.0. Derivation reproduces that same shape at the current settings, so they remain consistent, but do not treat them as generated by the current specs.

**Every story lives in its own workspace** under `stories/<story-id>/`, and every path in `paths` except `stories_root` is resolved relative to it (FR-42). `config.json` and `specs/` stay at the repository root and are shared; a run reads the configuration and never writes it. The one existing novel is `stories/the-cold-lamp/`.

## Rules that are easy to break here

Every one of these was broken at least once, either by the specs or by the run.

**Never write outside the current story's workspace** (FR-45). A path that is absolute, or that traverses above `derived.story_root`, is rejected before the first write (I-9). One story overwriting another is the defect the workspace layout exists to remove, and it was silent when it happened.

**Never write a literal where a parameter belongs** (FR-20). Not in a prompt, not in code, not in a document. `20 pages`, `4/12/4`, `two retries`, `350 words` are all configuration. If a value is needed and is not in `config.json`, that is a defect in the config or in the requirement — not a licence to inline it.

**Derived values are computed, never stored** (TR-03b). `derived.chapter_sizes`, `derived.acts`, `derived.act_spans` and `derived.anchor_pages` come from the rules in functional §2.2 at load time. A derived value written back into `config.json` is a value that can go stale, which is the defect derivation exists to remove.

**Never silently ignore a supplied value** (FR-37). When `chapters` and `pages_per_chapter` conflict, `chapters` wins *and the supersession is reported*. A run that appears to ignore the config file is the original defect this design was rewritten to fix.

**Do not restate spec content in new files.** Cross-reference by FR/TR number. Two copies of a rule is two rules. The five agent files are the exception that proves it: behaviour lives there and *only* there, and §5 of the technical spec was cut back to wiring when they were written.

**One block of one agent definition is calibrated, and only through its tool.** Rule 2 of `page-writer.md` sits between `<!-- calibrated:length ... -->` markers and is rewritten by the loop of the self-improvement specification, through `python -m calibration.cli apply`, never by hand and never any other byte of that file. A candidate is validated in code first: no digit, still about length, within its ceiling. Everything outside those markers, in every agent file, is written by a person and reviewed as a diff.

**Never put a config value in an agent definition** (FR-47). An agent file may name a configuration path to say which value governs a rule; the value itself arrives in the invocation payload. This is the whole reason a static prompt file can still satisfy FR-20, and it is the easiest of these rules to break, because a number in a prompt reads as helpful.

**Never merge two call types into one invocation** (FR-46). Page and Consistency above all: that separation is TR-09, it is what retires the principal risk of v1.x, and the measured run failed it by running the check as a separate pass inside the same session. Form without substance is the documented failure, not a near miss.

**No agent writes anything but the staged bible** (FR-49). `bible-builder` writes into `paths.staging_dir`; the orchestrator commits at A7 and every other file in the workspace. An agent that could write is an agent that can leave the workspace inconsistent halfway through a judgement.

**A change to the specs is not finished until** it is recorded in §11.5 / §11 open issues, versioned in the version-history table, and re-checked against the V-01 to V-10 checklist. The procedure is in functional §11.4.

## Running the flow

Phases and steps are in functional §5. What that section cannot enforce:

Functional §5.0 now answers this step by step: every step is assigned either to code or to a named agent. What that table cannot enforce:

**What must be real code, not model judgement.** Config validation and derivation, the A6 gate arithmetic, page length (FR-10), the roster check (FR-11), `assemble(N)`, thread and arc replay, chapter balance, manuscript assembly. If any of these is *asserted* rather than *executed*, the run's claims about itself are worth nothing. The first run executed them and that is why its numbers are trustworthy.

**What is necessarily judgement, and who gets it.** K1–K7 consistency → `consistency-checker`. The continuity audit (FR-39) → `continuity-auditor`. The bible (FR-01 to FR-05) → `bible-builder`, in one invocation. The report (FR-19) → `closing-auditor`, over numbers it does not recompute. The anchor-reversal check at A6 (FR-27) is the one judgement with no agent of its own, which is OI-12.

**Delegate; do not do it yourself.** Writing a page in the session that is running the loop is the flat form this design replaced. It also makes the run unreadable afterwards: a delegated call is one labelled span, and a call made inline is indistinguishable from the orchestration around it.

**Two calls are orchestrator-owned and have no agent file** (technical §5): the extraction of the state record's summary, character states, threads and facts from the finished prose, and the chapter digest. They carry no narrative authority, and giving either an agent file would imply it did.

**Per page, in order:** read the beat → load only its declared sheets, within `context.max_characters_per_page` and `context.max_settings_per_page` → assemble in code → delegate to `page-writer` → mechanical check in code → delegate to `consistency-checker`, separate invocation → retry up to `control.max_retries_per_page`, then flag and continue → write the page file and append the state record **including `facts`**.

Label every delegation with its call type and its page, and a retry with its attempt number (FR-48). An unlabelled invocation is recoverable only from the run directory, and only by hand.

**At each chapter close:** continuity audit against the fact ledger *before* writing the digest, repair up to `control.max_continuity_repairs` with a `supersedes` record, then the digest within `context.chapter_digest_max_words`.

### Traps with measured evidence

- **Length binds from above.** Six of the run's seven retries were length failures, every one over the ceiling; mean page 392 words in a band of 280–420. Write to the target, not past it.
- **The cast ceiling is a scene ceiling.** A character whose sheet is not loaded cannot be written with voice or arc. `max_characters_per_page` decides how many people can hold a scene, not just payload size.
- **A page may name a character it does not stage** (FR-11, K7). Naming is allowed; acting and speaking are not. The code check is deliberately permissive — only the bible's full roster — because a word matcher cannot tell a mention from an entrance.
- **Digests are the compression risk.** They ran ~270 tokens each and the final chapter used that material. Bounding them harder buys budget and costs continuity (TI-07).

## Checks before committing a spec change

Run these; they catch what review misses.

- Every `group.key` in backticks across both specs exists in `config.json`, and no config key is unreferenced (checklist V-08).
- Every FR referenced is defined, and vice versa.
- Every Mermaid block: no node referenced in an edge that is never declared with a shape.
- No stale parameter names (`max_sheets_per_page`, `organization.acts`, `organization.pages_per_chapter` outside §2.2, `prompts/*.md`, `agents.py`).
- Every call type in technical §5 has exactly one file in `.claude/agents/`, and no file there is unreferenced (checklist V-12).
- No agent definition contains a configuration literal (V-13), and every step of functional §5 appears in the table of §5.0 (V-14).

- **The calibration loop is built**: `calibration/` and `tests/test_calibration.py`, driven by `loops/RUNBOOK.md`. It is the only code in the repository besides `ui/`. The orchestrator itself is still a session, not `run.py`.

- **TI-01 blocks approval** — `model.id` and `model.max_output_tokens` are `null`, so cost per run is unknown.
- **OI-07 / TI-10 are blocking for any unattended run** — the anchor-reversal gate is a lexical proxy and its failure mode is silent.
- **OI-10 / TI-14 and OI-11 / TI-15 were introduced by the delegated form**: an agent definition can carry neither a temperature nor an empty tool allowlist, so TR-10 has no mechanism and the FR-08 ceilings rest on instruction for the two most frequent call types.
