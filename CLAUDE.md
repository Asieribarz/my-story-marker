# CLAUDE.md

Specifications for an adventure-story generator: an orchestrator drives one model call per page, all durable state lives in files. **The system is not built yet.** This repository holds the specifications, the configuration, and the artefacts of one complete run that was orchestrated by hand.

Documents are written in English. Conversation may be in Spanish; the files are not.

---

## Where authority lives

Read in this order. When two disagree, the earlier one wins.

1. **`config.json`** — every control and organization value. The only place a number lives.
2. **`specs/functional_specification_story_agent.md`** — what the system does. FR-01 to FR-41.
3. **`specs/technical_specification_story_agent.md`** — how. TR-xx, invariants I-1 to I-8, build inventory (§12).
4. **`stories/the-cold-lamp/report.md`** — evidence from the run of 2026-09-15. **Never edit it.** It records what happened under specs v2.1, and rewriting it destroys the only measurement the project has.

Run artefacts — `bible/`, `pages/`, `state/`, `story.md` — were produced under config v2.0. Derivation reproduces that same shape at the current settings, so they remain consistent, but do not treat them as generated by the current specs.

**Every story lives in its own workspace** under `stories/<story-id>/`, and every path in `paths` except `stories_root` is resolved relative to it (FR-42). `config.json` and `specs/` stay at the repository root and are shared; a run reads the configuration and never writes it. The one existing novel is `stories/the-cold-lamp/`.

## Rules that are easy to break here

Every one of these was broken at least once, either by the specs or by the run.

**Never write outside the current story's workspace** (FR-45). A path that is absolute, or that traverses above `derived.story_root`, is rejected before the first write (I-9). One story overwriting another is the defect the workspace layout exists to remove, and it was silent when it happened.

**Never write a literal where a parameter belongs** (FR-20). Not in a prompt, not in code, not in a document. `20 pages`, `4/12/4`, `two retries`, `350 words` are all configuration. If a value is needed and is not in `config.json`, that is a defect in the config or in the requirement — not a licence to inline it.

**Derived values are computed, never stored** (TR-03b). `derived.chapter_sizes`, `derived.acts`, `derived.act_spans` and `derived.anchor_pages` come from the rules in functional §2.2 at load time. A derived value written back into `config.json` is a value that can go stale, which is the defect derivation exists to remove.

**Never silently ignore a supplied value** (FR-37). When `chapters` and `pages_per_chapter` conflict, `chapters` wins *and the supersession is reported*. A run that appears to ignore the config file is the original defect this design was rewritten to fix.

**Do not restate spec content in new files.** Cross-reference by FR/TR number. Two copies of a rule is two rules.

**A change to the specs is not finished until** it is recorded in §11.5 / §11 open issues, versioned in the version-history table, and re-checked against the V-01 to V-10 checklist. The procedure is in functional §11.4.

## Running the flow

Phases and steps are in functional §5. What that section cannot enforce:

**What must be real code, not model judgement.** Config validation and derivation, the A6 gate arithmetic, page length (FR-10), the roster check (FR-11), `assemble(N)`, thread and arc replay, chapter balance, manuscript assembly. If any of these is *asserted* rather than *executed*, the run's claims about itself are worth nothing. The first run executed them and that is why its numbers are trustworthy.

**What is necessarily judgement.** K1–K7 consistency (FR-12 to FR-14), the continuity audit (FR-39), the anchor-reversal check at A6 (FR-27). These go to a model — and must go to a *separate call* from the one that wrote the page (TR-09). The first run ran them as a separate pass but not against an independent endpoint; the form was satisfied and the substance was not. Do not repeat that and call it compliance.

**Per page, in order:** read the beat → load only its declared sheets, within `context.max_characters_per_page` and `context.max_settings_per_page` → assemble → write → mechanical check → consistency check → retry up to `control.max_retries_per_page`, then flag and continue → write the page file and append the state record **including `facts`**.

**At each chapter close:** continuity audit against the fact ledger *before* writing the digest, repair up to `control.max_continuity_repairs` with a `supersedes` record, then the digest within `context.chapter_digest_max_words`.

### Traps with measured evidence

- **Length binds from above.** Six of the run's seven retries were length failures, every one over the ceiling; mean page 392 words in a band of 280–420. Write to the target, not past it.
- **The cast ceiling is a scene ceiling.** A character whose sheet is not loaded cannot be written with voice or arc. `max_characters_per_page` decides how many people can hold a scene, not just payload size.
- **A page may name a character it does not stage** (FR-11, K7). Naming is allowed; acting and speaking are not. The code check is deliberately permissive — only the bible's full roster — because a word matcher cannot tell a mention from an entrance.
- **Digests are the compression risk.** They ran ~270 tokens each and the final chapter used that material. Bounding them harder buys budget and costs continuity (TI-07).

## Checks before committing a spec change

Run these; they catch what review misses.

- Every `group.key` in backticks across both specs exists in `config.json`, and no config key is unreferenced (checklist V-08).
- Every FR referenced is defined, and vice versa.
- Every Mermaid block: no node referenced in an edge that is never declared with a shape.
- No stale parameter names (`max_sheets_per_page`, `organization.acts`, `organization.pages_per_chapter` outside §2.2).
